# Эксперимент: полный файл как контекст ревью — как прогнать

> **Временный файл.** Удаляется вместе с веткой после эксперимента (spec 011).
> Спека и результат остаются в `specs/011-full-file-context.md`.

Проверяем один вопрос: **становится ли ревью лучше, если показать модели файл целиком,
а не только куски diff'а.** Ответ должен быть в цифрах, а не в ощущениях.

---

## 0. Перед прогоном — два решения (5 минут, без кода)

**Список PR.** Нужно ~10 номеров. Лучше **уже смёрдженных или закрытых**: их дифф не
изменится между прогонами, и никого не потревожим. Состав:

| Сколько | Какие | Зачем |
|---|---|---|
| 3–4 | где были ложные срабатывания | проверить, ушли ли они |
| 3–4 | обычные, рядовые | **по ним и принимается решение** |
| 2–3 | крупные, многофайловые | посмотреть на откаты и токены |

Метрики считаются по этим группам **раздельно**. Если считать вместе, вывод будет
предрешён: PR первой группы отобраны именно по признаку «здесь не хватило контекста».

**Критерий успеха.** Записать до прогона, иначе результат подгонится под ожидание.
Предложение из спеки:

> Режим `file` принимаем, если ложные срабатывания класса «не хватило контекста» упали
> хотя бы вдвое, число верных замечаний по изменённым строкам не упало, а токены на PR
> выросли не больше чем в 2,5 раза.

## 1. Подготовка на сервере (один раз)

```bash
git fetch && git checkout experiment/full-file-context
mkdir -p ~/jarvis_experiment/{A_hunks,B_file,A2_hunks}
```

Проверить, что рядом лежит **боевой** `styleguide.md` — тот же, что у прода. С заглушкой
эксперимент бессмысленен: половина ложных срабатываний растёт именно из реальных правил.

**Стайлгайд на время прогонов не трогаем.** Он влияет на оба режима одинаково, поэтому
разница между ними остаётся чистой. Переписывание правил — отдельная работа после.

## 2. Прогон

Три прохода по одному и тому же списку PR. Для каждого PR — одна строка, меняется номер.

**A — как в проде (ханки):**
```bash
python3 review_cli.py --project ПРОЕКТ --repo РЕПО --pr-id 42 \
    --dry-run --out-dir ~/jarvis_experiment/A_hunks --context-mode hunks
```

**B — полный файл:**
```bash
python3 review_cli.py --project ПРОЕКТ --repo РЕПО --pr-id 42 \
    --dry-run --out-dir ~/jarvis_experiment/B_file --context-mode file
```

**A2 — повтор режима A на 5 любых PR из списка:**
```bash
python3 review_cli.py --project ПРОЕКТ --repo РЕПО --pr-id 42 \
    --dry-run --out-dir ~/jarvis_experiment/A2_hunks --context-mode hunks
```

Зачем A2: температура модели не ноль, два прогона **одного и того же** режима дают разные
ответы. Разброс A↔A2 — это шум. Если разница A↔B не больше шума, значит ответа нет,
а не «стало лучше».

**Порядок:** чередуй режимы по PR (A, B, потом B, A на следующем). Ответ Феникса частично
кэшируется, и одинаковый порядок систематически удешевлял бы второй прогон.

Лог стоит сохранять: `... --pr-id 42 2>&1 | tee ~/jarvis_experiment/log_A_42.txt`.

### Что проверить на самом первом запуске

- В логе строка `Режим: контекст=..., dry-run=ДА`.
- В логе есть `🧪 dry-run: комментарий не опубликован`, и **нет** ни одного успешного
  POST в Bitbucket.
- Открыть PR в браузере — новых комментариев нет.

Только после этого запускать остальные девять.

## 3. Что окажется в отчётах

`~/jarvis_experiment/A_hunks/pr_42.jsonl` — одна строка = один JSON:

| `type` | Что внутри |
|---|---|
| `run` | режим прогона, число файлов, размер стайлгайда |
| `file` | по каждому файлу: фактический режим, причина отката, размер, токены, число обращений к Фениксу, сколько замечаний отфильтровано |
| `comment` | замечание, которое бот **опубликовал бы** |
| `filtered` | замечание, отсечённое как «не на изменённой строке» |

Содержимого файлов и промптов в отчёте нет — только замечания и метаданные.

**Единица анализа — файл, а не PR.** Из-за откатов один прогон бывает смесью режимов:
поле `mode` в записи `file` говорит, как этот файл ревьюился на самом деле. Сравнивать
надо файлы, у которых `mode` действительно разный.

Отдельно посмотреть в `file`:
- `fallback_reason` — если откатов много, лимит `REVIEW_FILE_MAX_CHARS` подобран неверно;
- `hunk_truncated` — в режиме A файл резался по 400 строк. Такие файлы из главной метрики
  лучше исключить: иначе выигрыш B будет частично не про контекст, а про снятие обрезки;
- `usage.model` — если версия модели между прогонами сменилась, сравнение недействительно.

## 4. Разметка

Скопировать `~/jarvis_experiment/` к себе и свести оба набора в одну таблицу:

```
pr_id · файл · строка · текст замечания · вердикт
```

**Колонку с режимом при разметке скрыть**, открыть после. Иначе рука сама тянется
засчитывать в пользу гипотезы — это не про честность, это про то, как устроено внимание.

Вердикты — пять, больше не надо:

| Вердикт | Когда |
|---|---|
| `верно` | замечание по делу |
| `ложное: не хватило контекста` | опровергается самим файлом (прагма выше, валидация выше, путь из переменной) |
| `ложное: другое` | модель ошиблась не из-за контекста |
| `не про изменённые строки` | замечание к чужому коду |
| `верное, но не на изменённой строке` | для записей `filtered`: по сути правильно, но вне diff'а |

Последняя категория нужна, чтобы фильтр не занижал режим `file`: видя весь файл, модель
чаще ставит номер контекстной строки, и часть таких замечаний осмысленна.

**Итог — по четыре числа на режим** (верных / ложных-по-контексту / прочих ложных /
токенов на PR), отдельно по «обычным» и «известным» PR.

## Если что-то пошло не так

| Симптом | Причина |
|---|---|
| `--dry-run требует --out-dir` | путь не задан. Так и задумано: без него отчёт лёг бы в клон репозитория |
| `--out-dir должен быть абсолютным` | `~` в кавычках не раскрылся. Писать без кавычек или полный путь |
| В отчёте у всех файлов `mode: hunks` | смотреть `fallback_reason`: не получен файл, не сошлись номера или превышен лимит |
| `номера строк не сошлись` на всех файлах | дифф PR считается не от той версии, что отдаёт raw. Это ответ на главное допущение эксперимента — записать и обсудить, а не чинить на ходу |
| `Феникс не ответил на полный файл` | вход не влез. Бот сам повторит ханками; в отчёте будет `fenix_calls: 2` |
| Прогон долгий | обращения к Фениксу идут строго по очереди (семафор = 1). Так и надо: иначе прогон ударит по общей квоте |
