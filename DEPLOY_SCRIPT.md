# Развёртывание бота скриптом (без Docker) — в т.ч. переезд на другой сервер

Шпаргалка для инженера, который поднимает бота на сервере обычным процессом
Python. Значения в `<...>` подставить свои — здесь они намеренно обезличены.

> ⚠️ Бот сам `.env` не читает (в зависимостях нет dotenv) — переменные
> экспортируются в окружение перед запуском (шаг 5).

---

## 0. До переезда: что согласовать

Новый сервер — это **новые сетевые доступы**. Ничего из списка ниже не
настраивается «на месте» — только заявкой администраторам и ИБ.

| Направление | Зачем |
|---|---|
| Bitbucket → `<новый сервер>:<порт>` | вебхуки о PR |
| новый сервер → Bitbucket REST API | забрать diff и файлы, опубликовать комментарии |
| новый сервер → Феникс | ревью моделью |
| новый сервер → mcp-drospr | perlcritic и граф вызовов (если используются) |

Не использовать туннели, проброс портов, прокси и «прыжки» через другие
серверы в обход согласованных доступов. Нет доступа — заявка, а не обходной путь.

**Внесение кода.** Файлы бота вносятся в контур только после согласования с ИБ
и антивирусной проверки. Для заявки — перечень файлов с SHA-256:

```bash
sha256sum pr_review_bot.py profiles.py review_cli.py mcp_client.py \
  bitbucket_files.py diff_filter.py perlcritic_severity.py styleguide_rules.py \
  changed_symbols.py review_prefs.py > SHA256SUMS
```

На сервере после переноса — сверка: `sha256sum -c SHA256SUMS` (все строки `OK`).

## 1. Пакеты

Нужен Python ≥ 3.9 и три пакета: `fastapi`, `uvicorn`, `requests`. Ставить только
из согласованных источников (системные пакеты ОС или внутренний Nexus).

```bash
python3 --version
python3 -c "import fastapi, uvicorn, requests; print('ok')"
```

## 2. Файлы

Положить в одну папку, например `<папка бота>`:

| Файл | Обязателен | Роль |
|---|---|---|
| `pr_review_bot.py` | да | бот (точка входа) |
| `profiles.py` | **да** | профили стеков — без него бот не стартует |
| `review_cli.py` | для ручного запуска | ревью PR из консоли |
| `mcp_client.py`, `bitbucket_files.py`, `diff_filter.py`, `perlcritic_severity.py`, `styleguide_rules.py`, `changed_symbols.py` | для Perl-слоёв | без них бот работает, но **молча** без perlcritic, codestyle, impact и полного файла |
| `review_prefs.py` | желательно | метка `@jarvis` в описании PR |
| `styleguide.md`, `styleguide_rules.txt` | для Perl | стайлгайд и regex-правила |
| `profiles.json` | нет | исключения профилей (шаг 4) |

Проверка, что модули на месте:

```bash
cd <папка бота>
python3 -c "import pr_review_bot as b; print('INSPECTOR_AVAILABLE =', b.INSPECTOR_AVAILABLE)"
# ожидаем: INSPECTOR_AVAILABLE = True
```

## 3. `.env`

Создать на сервере, в git и в переписку не класть. Шаблон со всеми
переменными и пояснениями — `.env.example`. Минимум:

```ini
BITBUCKET_URL=<адрес Bitbucket>
BITBUCKET_TOKEN=<токен сервисной учётки>
FENIX_URL=<адрес Феникса>
FENIX_TOKEN=<токен Феникса>
FENIX_MODEL=<модель>
# Perl-слои (если используются)
MCP_DROSPR_URL=<адрес mcp-drospr>
PERLCRITIC_ENABLED=1
STYLEGUIDE_RULES_PATH=<папка бота>/styleguide_rules.txt
# Профили — абсолютный путь (или не задавать: возьмётся profiles.json рядом с ботом)
PROFILES_PATH=<папка бота>/profiles.json
```

## 4. `profiles.json` — когда нужен

Без файла бот работает на умолчаниях: Perl-файлы — `perl-lite` (без impact),
остальное — `generic`, мусор (lock-файлы, бандлы, картинки, `node_modules/`…) —
пропуск. Файл нужен для исключений, пример — `profiles.example.json`:

| Нужно | Что написать |
|---|---|
| impact для репо, чей индекс залит в mcp-drospr | `"PROJ/repo": {"perl_profile": "perl"}` |
| не проверять папку | `"paths": [{"glob": "docs/**", "profile": "skip"}]` |
| ревьюить Perl-папку как generic (или наоборот) | правило папки с нужным профилем |
| выключить ревью репо целиком | `"PROJ/repo": {"enabled": false}` |
| не проверять тип файлов во всех репо | `"skip": ["*.pb.go"]` |

> ⚠️ **Миграция impact.** Impact работает **только** у репо с
> `"perl_profile": "perl"`. Если раньше был включён `IMPACT_ENABLED=1` — прописать
> этот репо в `profiles.json`, иначе impact пропадёт.

Проверить конфиг и профиль конкретного файла — без запуска ревью:

```bash
cd <папка бота>
set -a; . ./.env; set +a
python3 -c "import profiles; profiles.load(); print(profiles.status())"
# ok — конфиг загружен; absent — файла нет (умолчания); error — причина строкой выше

python3 -c "import profiles as p; c=p.load(); r=c.repo('PROJ/repo'); print(p.pre_profile('front/Form.tsx', '', r, c))"
# ('generic', 'по умолчанию')
```

Правки `profiles.json` подхватываются на следующем PR, рестарт не нужен.

## 5. Запуск

```bash
cd <папка бота>
set -a; . ./.env; set +a
nohup python3 -m uvicorn pr_review_bot:app --host 0.0.0.0 --port <порт> > bot.log 2>&1 &
```

Если терминал портит символ `&` при вставке — обернуть в `bash -c`:

```bash
bash -c 'set -a; . ./.env; set +a; nohup python3 -m uvicorn pr_review_bot:app --host 0.0.0.0 --port <порт> > bot.log 2>&1 &'
```

Остановка и перезапуск:

```bash
pkill -f "uvicorn pr_review_bot:app"
# затем снова команда запуска
```

Первые PR на новом сервере разумно прогнать с `JARVIS_DRY_RUN=1` и
`JARVIS_DRY_RUN_DIR=<абсолютный путь вне клонов репо>`: бот всё делает, но
ничего не публикует, а пишет в отчёт, что опубликовал бы.

## 6. Проверка

```bash
curl http://localhost:<порт>/health
```

Ожидается: `"status": "ok"`, `"tokens_loaded": true`, `"dry_run"` — как задумано,
`"profiles_config"` — `ok` или `absent`.

При старте в `bot.log`: `✅ Конфиг загружен…`, `⚙️ Контекст ревью: …`,
`⚙️ Профили стеков: <состояние> (<путь>)`.

## 7. Вебхук: настройка и проверка, что всё доходит

> Проверка — только штатными средствами: кнопка проверки в Bitbucket, `/health`
> бота, тестовый PR и логи. **Не** сканировать порты и хосты и не «прозванивать»
> сеть (`nc -z`, `nmap`, `Test-NetConnection`, перебор портов) — это нарушение
> правил ИБ. Не доходит — заявка администраторам (приложение А), не обходной путь.

### 7.1 Настроить вебхук (администратор репозитория или проекта Bitbucket)

Настройки репозитория → **Webhooks** → создать (или изменить существующий):

| Поле | Значение |
|---|---|
| Name | `JARVIS PR Review` |
| URL | `http://<новый сервер>:<порт>/webhook` |
| Secret | пока пусто; появится с подписью вебхука (spec 018) |
| События | **Pull request → Opened**, **Source branch updated**, **Modified** |
| Active | включён |

Другие события не нужны: бот их принимает, но игнорирует.

### 7.2 Проверка по шагам — от сервера наружу

Идти строго по порядку: каждый шаг проверяет одно звено. Первый провалившийся
шаг и есть место проблемы.

| # | Что проверяем | Как | Ожидаемо | Если нет |
|---|---|---|---|---|
| 1 | Бот запущен и видит конфиг | на сервере: `curl http://localhost:<порт>/health` | `"status":"ok"`, `"tokens_loaded":true` | процесс не запущен или `.env` не экспортирован (шаг 5) |
| 2 | Bitbucket достаёт до бота | в форме вебхука — кнопка **Test connection** (в Bitbucket Data Center), либо история запросов вебхука | ответ `200`; в `bot.log` строка `📨 Получен webhook: …` (тестовое событие бот принимает и игнорирует) | запрос не дошёл: нет сетевого доступа Bitbucket → сервер, либо неверный URL/порт. **Заявка** |
| 3 | Бот достаёт до Bitbucket API | открыть тестовый PR (см. ниже) | в `bot.log`: `📂 Файлов в PR #…` | `Не удалось получить diff` → нет доступа сервер → Bitbucket API или у токена нет прав Repo:Read. **Заявка** / проверить токен |
| 4 | Бот достаёт до Феникса | тот же PR | в `bot.log`: `📥 Ответ Феникса: finish_reason=…` | `Феникс не ответил` / ошибка соединения → нет доступа к Феникс или неверный токен. **Заявка** / проверить токен |
| 5 | Бот достаёт до mcp-drospr (если Perl-слои включены) | тестовый PR с `.pm`-файлом | в сводке есть `[perlcritic]`, нет пометки «mcp-drospr недоступен» | пометка в сводке → нет доступа к mcp-drospr. **Заявка** |
| 6 | Бот может публиковать | тот же PR, `JARVIS_DRY_RUN=0` | в PR появились комментарии и сводка | нет прав PR:Write у сервисной учётки |

**Тестовый PR.** В тестовом репозитории, к которому подключён вебхук: ветка с
небольшой правкой — один `.pm` и один не-Perl файл (например `.js`), PR в основную
ветку. Заголовок **без** `WIP` (иначе бот будет ждать снятия метки). Ожидаемо в
сводке: `🧭 Профили: perl-lite 1 · generic 1`.

Шаги 3–6 можно пройти и без нового PR — повторно отправить событие по уже
существующему PR прямо с сервера, на свой же бот:

```bash
curl -s -X POST http://localhost:<порт>/webhook -H 'Content-Type: application/json' \
  -d '{"eventKey":"pr:opened","pullRequest":{"id":<номер PR>,"title":"test",
       "toRef":{"repository":{"slug":"<repo>","project":{"key":"<PROJECT>"}}},
       "fromRef":{"latestCommit":"<хеш последнего коммита ветки PR>",
                  "repository":{"slug":"<repo>","project":{"key":"<PROJECT>"}}}}}'
# ожидаем {"status":"ok","pr_id":<номер PR>}, дальше — смотреть bot.log
```

Без `fromRef` ревью тоже пройдёт, но без полного файла и perlcritic — для
проверки шага 5 `fromRef` нужен.

Это запрос к **своему** боту на localhost, он не проверяет сеть — он запускает
обычное ревью, а уже бот ходит в Bitbucket и Феникс по выданным доступам.

### 7.3 Поэтапный запуск: сначала демо-репо, потом остальные

Какие репозитории ревьюит бот, определяет **то, где настроен вебхук** на этот
сервер: события приходят только от них. Поэтому пилот — это порядок подключения
вебхуков, отдельного флага в боте не нужно. Старый сервер всё это время
продолжает обслуживать боевые репозитории как раньше.

| Этап | Вебхук на новый сервер | Режим бота | Переход дальше, когда |
|---|---|---|---|
| 1. Демо, тихо | только **демо-репо** | `JARVIS_DRY_RUN=1` | 7.2 шаги 1–5 пройдены; в dry-run-отчёте по тестовым PR профили и замечания такие, как ожидалось |
| 2. Демо, вживую | только демо-репо | `JARVIS_DRY_RUN=0` | 7.2 шаг 6 пройден; комментарии и сводка в PR выглядят правильно, дублей нет |
| 3. Боевые репо | боевые репозитории — **переключить** с старого сервера | `JARVIS_DRY_RUN=0` | — |

На этапе 3:
1. Администратор меняет URL вебхука боевых репозиториев на новый сервер.
2. **Старый бот остановить сразу после переключения** — два живых бота на одном
   репо дают двойные комментарии.
3. Убедиться по первому боевому PR, что пришло ревью.

Новые команды (репозитории, где бота раньше не было) подключаются уже после
этапа 3 и только когда включена подпись вебхука (spec 018).

> Если вебхук настроен на уровне **проекта** Bitbucket (на все репозитории
> сразу), «только демо-репо» так не сделать — для пилота вебхук на демо-репо
> заводится отдельно, на уровне репозитория.

Смена режима `JARVIS_DRY_RUN` — правка `.env` и перезапуск (шаг 5).

Ожидаемо после обновления: в уже открытых PR первый пуш даст новые комментарии к
не-Perl файлам рядом с прежними (сменился промпт — дедуп не узнаёт новый текст).
Один раз.

**Откат:** остановить новый процесс, вернуть URL вебхука на старый сервер,
запустить там прежнюю версию.

## 8. Диагностика: симптом → куда смотреть

Логи и dry-run-отчёты содержат код и пути репозиториев — **за периметр не
выносятся**. Разбор — на месте; наружу — только описание симптома без кода и путей.

| Симптом | Куда смотреть |
|---|---|
| Бот молчит на PR | `bot.log`: пришёл ли вебхук (`📨 Получен webhook`); `⏸️ … ревью выключено в профилях`; `⏸️ … черновик` |
| Бот вообще не отвечает | `curl …/health`; жив ли процесс: `pgrep -af "uvicorn pr_review_bot"` |
| Бот не стартует, `ModuleNotFoundError: profiles` | рядом с `pr_review_bot.py` нет `profiles.py` |
| Файл не проверен | строка лога `🧭 <файл>: профиль skip (<причина>)`; строка `⏭️ Пропущено по правилам` в сводке PR |
| На файле не тот промпт | строка лога `🧭 <файл>: профиль <…> (<причина>)` — правило папки, расширение или shebang; проверить командой из шага 4 |
| Нет perlcritic на Perl-файле | профиль в логе (`generic` → правило папки или нет расширения); `INSPECTOR_AVAILABLE` (шаг 2); `PERLCRITIC_ENABLED`, `MCP_DROSPR_URL`; строка `mcp-drospr недоступен` |
| Нет impact | у репо в `profiles.json` `"perl_profile": "perl"`; `IMPACT_ENABLED=1`; индекс залит в mcp-drospr |
| Правка `profiles.json` не применилась | `/health` → `profiles_config`: `error` — файл битый, причина в `bot.log` (`❌ profiles: …`); `absent` — не найден по `PROFILES_PATH` |
| Файл помечен «показана не вся правка» | `Diff обрезан` в логе — сработал `MAX_DIFF_LINES` или `DIFF_MAX_CHARS` |
| Замечаний ИИ меньше, чем ожидалось | строка сводки `Замечаний ИИ сверх лимита`; метка `@jarvis` в описании PR; `POST_MIN_SEVERITY` |
| Странные или шумные замечания | `JARVIS_DRY_RUN=1` + ручной прогон `review_cli.py` по этому PR, смотреть JSONL-отчёт: что нашла модель, что отфильтровано и почему |
| Новые комментарии на старом PR после обновления | ожидаемо один раз (см. 7.3) |
| `Test connection` в Bitbucket не проходит | сетевой доступ Bitbucket → сервер не выдан или неверный URL/порт — заявка (приложение А) |

## Приложение А. Шаблон заявки на сетевые доступы

> Тема: доступы для сервиса автоматического ревью PR на сервере `<новый сервер>`
>
> Прошу предоставить сетевые доступы для сервиса автоматического ревью
> pull request (внутренний сервис, без доступа в интернет):
>
> | № | Источник | Назначение | Порт / протокол | Назначение доступа |
> |---|---|---|---|---|
> | 1 | `<Bitbucket>` | `<новый сервер>` | `<порт>`/HTTP | входящие вебхуки о pull request |
> | 2 | `<новый сервер>` | `<Bitbucket>` | `<порт>`/HTTP(S) | чтение diff и файлов PR, публикация комментариев (REST API) |
> | 3 | `<новый сервер>` | `<Феникс>` | `<порт>`/HTTP(S) | запросы к внутренней модели ревью |
> | 4 | `<новый сервер>` | `<mcp-drospr>` | `<порт>`/HTTP | статический анализ Perl (если используется) |
>
> Сервисная учётка Bitbucket: права Repo:Read и PR:Write (без Repo:Write).
> Сервис не принимает соединений, кроме вебхуков Bitbucket, и не открывает
> других портов.

Если на прежнем сервере доступы уже были — в заявке сослаться на прежнюю: это
перенос существующего сервиса, а не новый.
